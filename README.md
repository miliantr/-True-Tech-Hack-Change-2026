# МТС EnergyTool — ИИ-консультант

Прототип помогает посетителю разобраться в решениях EnergyTool и сформировать тестовую заявку с резюме разговора. Консультация опирается на предоставленную базу знаний. Один движок используется в веб-чате и в конкурсном CSV-сабмите.

## Запуск и проверка

Положите полученный от организаторов `knowledge-base.zip` в `Данные/` рядом с `compose.yaml`. Архив базы знаний распространяется отдельно от исходного кода.

Запустите все компоненты одной командой:

```sh
docker compose up --build
```

Откройте [http://localhost:8000](http://localhost:8000). Для запуска без Docker достаточно Python 3.12:

```sh
python app.py
```

Порт по умолчанию `8000`. Compose публикует его только на loopback интерфейсе. Для другого порта задайте `HOST_PORT` и открывайте `http://localhost:<порт>`. SQLite и ключ проверяющего сохраняются в каталоге `runtime/` при локальном запуске или в Docker volume `history`.

Собирайте образ на локальном Docker Desktop или другом доверенном локальном Docker. Образ содержит предоставленный `knowledge-base.zip`, чтобы запуск не зависел от настроек общего доступа к папкам Windows. Храните этот образ локально и пересобирайте его при обновлении базы. В архивах сдачи база отсутствует.

1. Опишите задачу, например «У нас три склада, хотим видеть потребление каждого». В режиме модели задайте уточняющий вопрос, затем вернитесь к исходной теме.
2. Откройте «Заявка» и введите вымышленные ФИО, номер и компанию. Проверьте подтверждение сохранения.
3. Нажмите «Новый диалог». Убедитесь, что сообщения прошлого разговора исчезли из активного чата.
4. Откройте «Проверка диалогов» и введите `REVIEW_TOKEN` из вашего окружения. Если переменная пуста, используйте ключ из `runtime/reviewer-token.txt`. В Docker он доступен локальной командой `docker compose exec energytool cat /app/runtime/reviewer-token.txt`.
5. Выберите прошлый диалог. Откройте резюме заявки и блок отладки с временем поиска, общим временем ответа и выбранными фрагментами. Диалоги без заявки тоже сохраняются.

Сделайте ещё один запрос без заявки и закройте чат кнопкой ×. После открытия нового чата предыдущий разговор останется в архиве.

## Подключение модели

Скопируйте `.env.example` в `.env` для веб-прототипа. Заполните адрес **разрешённого для материалов кейса** прокси, ключ и имя модели. На конкурсной платформе эти параметры передаются в окружении автоматически. Передача базы знаний на другие сервисы ограничена условиями кейса.

| Переменная | Назначение |
|---|---|
| `LLM_BASE_URL` или `OPENAI_BASE_URL` | Базовый URL OpenAI-совместимого прокси, включая префикс API, если он нужен. |
| `LLM_API_KEY` или `OPENAI_API_KEY` | Ключ прокси. |
| `LLM_MODEL`, `OPENAI_MODEL` или `GEN_MODEL` | Идентификатор модели. В автоматической оценке организаторы используют Qwen3.8-27B. |
| `DATA_DIR` | Папка данных. Для чата по умолчанию `Данные`, для сабмита `data`. |
| `RETRIEVAL_MODE=hybrid` и `EMB_MODEL` | Опциональный поиск с BAAI/bge-m3. Эмбеддинги документов создаются при запуске. |
| `USE_RERANKER=1` и `RERANKER_MODEL` | Опциональный Qwen3 Reranker 8B через `/rerank`. |
| `TOP_K`, `RERANKER_TOP_N` | Число кандидатов и проходящих фрагментов при включённом реранжировании. Без реранжирования поиск выбирает шесть основных фрагментов. Дополнительно включаются продуктовые оговорки. |
| `MAX_WORKERS`, `API_TIMEOUT`, `RUN_BUDGET_SECONDS` | Параллелизм, тайм-аут вызова и бюджет времени CSV-раннера. |
| `MAX_TOKENS`, `TEMPERATURE` | Параметры генерации. |
| `HOST`, `PORT`, `RUNTIME_DIR`, `REVIEW_TOKEN` | Параметры веб-сервера, хранения и проверки. |

Без реквизитов веб-интерфейс явно показывает режим предпросмотра с фрагментом найденного источника. В конкурсном режиме требуется модель. Реквизиты никогда не нужны в браузерном коде.

## Сабмит для автоматической оценки

```sh
python package_submission.py
```

Загрузите `dist/submission.zip` как Python-сабмит. Файлы лежат в корне. Платформа предоставляет `DATA_DIR/questions.csv` с `id,question` и `knowledge-base.zip`, затем запускает `solution.py`. Раннер сохраняет `submission.csv` в текущем каталоге с колонками `id,answer`. Он сохраняет порядок и исходный вид ID, записывает непустой ответ на каждую строку и обрабатывает тесты независимо.

Для ручной локальной проверки скопируйте `Данные/demo_questions.csv` как `questions.csv` в отдельный каталог вместе с `knowledge-base.zip`. Задайте `DATA_DIR` и параметры модели в окружении, затем запустите `python solution.py`. Переменная `ALLOW_PREVIEW=1` позволяет проверить формат CSV без модели. Такой CSV служит только локальной проверкой формата.

## Архитектура

`retrieval.py` читает весь архив и строит индекс фрагментов с заголовками. Лексический поиск использует BM25, короткие аббревиатуры и признаки для русских словоформ. При включении гибридного режима результаты объединяются с векторным поиском. При сбое эмбеддингов или реранжирования остаётся лексический порядок.

`consultant.py` подаёт модели источники и историю текущей сессии. Инструкции требуют различать факты о продукте и слова клиента, сохранять ограничения и единицы измерения, задавать уточнение или предлагать специалиста при нехватке сведений. Типовой ответ генерируется одним вызовом `/chat/completions`.

`app.py` обслуживает веб-чат, `storage.py` хранит сообщения и заявки в SQLite. Новый диалог получает собственный идентификатор и токен. Резюме заявки включает исходный запрос, последние уточнения клиента, последнюю консультацию и следующий шаг. Контакты из формы остаются в SQLite. История и отладка доступны по ключу проверяющего.

## Проверки и ограничения

Для локальных тестов добавьте полученный от организаторов `demo_questions.csv` в `Данные/` и распакуйте туда содержимое `knowledge-base.zip`, сохранив исходные папки. Эти файлы распространяются отдельно от репозитория.

```sh
python -m unittest discover -s tests -v
python evaluate.py
python evaluate.py --suite development --compare
python evaluate.py --suite holdout
```

Интеграционные тесты распаковывают конкурсный ZIP и запускают 18 демо-вопросов через локальный имитатор API в лексическом и гибридном режимах. `evaluate.py` измеряет наличие опорных фрагментов и время поиска. Отчёты сохраняются в `test-results/`. В `tests/scenarios.json` находятся 40 дополнительных сценариев с критериями проверки, включая 10 отложенных вопросов и четыре сценария формы заявки.

Для сравнения реальных эмбеддингов и реранжирования на разрешённом прокси добавьте `--proxy` к `--compare`. Для сохранения ответов текущей конфигурации добавьте `--proxy --generate` без `--compare`. Ответы проверяются человеком по полям `expect` и `avoid`. Порядок проверки и сдачи описан в [REVIEW.md](REVIEW.md).

Сетевая интеграция с организаторами и результат скрытой оценки требуют доступа к их среде. Веб-демо рассчитано на один локальный процесс. В длинном диалоге в модель передаётся до 14 000 символов последних сообщений, при этом полный разговор остаётся доступен проверяющему. Инструкции и источники снижают риск неподтверждённых утверждений, но не заменяют проверку экспертом.

## Пилот на сайте EnergyTool

Разместить виджет в контуре МТС и подключить утверждённую версию базы знаний. Согласовать обработку контактов и правила хранения истории. После подтверждения пользователем передавать заявку в утверждённую очередь менеджеров с идентификатором сессии и резюме. На пилоте измерять долю квалифицированных заявок, принятие заявок менеджерами, время первичного разговора и ошибки консультации.

Для финальной сдачи используйте `dist/EnergyTool-final.zip` с исходным кодом, инструкцией и `EnergyTool.pdf`. В обоих архивах отсутствуют исходная база, тестовые вопросы, данные диалогов и секреты.
